Evidence behind the behaviour

Verification

A useful contract must hold when delivery fails, when a process stops and when a source tries again.

Check the state an application receives.

Several levels of evidence

Focused strategy tests check individual decisions. Service tests exercise real interfaces. Crash tests start a separate ZooGlass process, terminate it at controlled boundaries and inspect the recovered result.

Workbench adds controlled delivery scenarios. The vehicle demo makes some of their effects visible; it is not the only evidence for the core.

Repeatable scenarios with Workbench

A delivery problem is much easier to investigate when you can reproduce it. Workbench is a deterministic timeline simulator: a scenario fixes the scheduled actions and their order, including what sources send, when connections change and what the resulting views should contain.

Describe the situation

Define the view, event sequence, client actions and expected results in a scenario file. Make delayed, duplicated or missing reports intentional parts of the run.

Run against ZooGlass

Workbench starts the prepared service, connects the sources and clients, and executes the scenario. Disconnects and reconnects exercise real connections.

Check what happened

View checks compare the service’s exposed state with the expected JSON. The scenario gives you a repeatable check to rerun when the configuration or implementation changes.

For example: a late position and a disconnected viewer

Send a newer position before an older report. Check that the latest-position field keeps the newer value while ordered history includes both. Disconnect a viewer, continue sending updates, then reconnect it and check the snapshot it receives.

This makes the behaviour useful beyond a one-off demonstration: you can explain the rule, inspect its outcome and retain the scenario as a regression check.

Run a Workbench scenario ↗

Workbench verifies scenario outcomes through the service’s interfaces. The focused service and crash tests below provide additional evidence for the core contracts.

What the checks ask

Did a lost acknowledgement repeat the effect?

Stop the service before commit, after commit but before acknowledgement, and after acknowledgement. Restart it, retry the publication and check the durable view and receipt.

Database crash recovery tests ↗

Did a withdrawn fact come back?

Crash around fact retraction and retirement commits. Check that recovered projections, tombstones, retirement floors and retry outcomes agree.

Fact crash tests ↗

Do the policies still agree after a crash?

Feed two scoreboards with different revision policies. Confirm missing reports, withdraw a goal, then crash after commit but before the receipt. After restart, check the scores and gaps together. A delayed older revision fills one gap without restoring the withdrawn goal.

Combined match acceptance ↗

Is ageing still meaningful after recovery?

Check receipt-age state through restart and clock changes, including the distinction between a recovered value and a newly received contribution.

Freshness recovery tests ↗

Can invalid state become a ready service?

Recovery tests check persisted state and configuration compatibility. Invalid recovery must fail rather than expose a partially recovered view.

Storage recovery tests ↗

Do different views retain different facts?

Exercise independent revision policies, bounded collections and explicit retirement. Check the results together with publication and freshness behaviour.

Fact composition tests ↗

What does a returning viewer receive?

Disconnect a viewer, change the service state and reconnect it. Verify the fresh baseline before sending more events, including after a service restart with memory or database storage.

Client recovery acceptance ↗

Does revoked access stay revoked?

Withdraw one viewer’s permission while another keeps receiving updates. Check denial, expiry, queued delivery and fresh decisions after reconnect or restart. Transport checks measure the release boundary; browser checks verify that protected content clears.

Authorisation evidence ↗

Evidence links are pinned to main revision 4ec47e7. Crash checks use the real database driver and process termination; they do not simulate hardware power loss.
