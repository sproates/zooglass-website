Workbench: deterministic timeline simulation

Workbench is a deterministic timeline simulator that runs ZooGlass’s actual reconciliation code. It controls virtual time and the order of execution, letting you reproduce supported event sequences and check exactly how the runtime responds. Your expected results are assertions; ZooGlass still makes the decisions.

Control the difficult sequence

Specify the events, supported faults and expected views. Advance virtual time to exercise freshness deadlines, lost receipts and retries, or a restart where the selected profile supports it.

Check the real runtime

Execute production strategy code under controlled scheduling. Compare observed results with explicit expectations, and retain the ordered trace of what happened.

Replay the evidence

Keep the inputs, run and trace in a portable bundle. Replay executes the scenario again and compares newly emitted records with the saved trace. It detects divergence instead of playing back stored answers.

What this means for ZooGlass

A hard-to-reproduce sequence can become a repeatable regression check. You can verify how source priority, corrections, freshness or retained receipt identity behave in supported scenarios, and keep the evidence with the configuration and runtime that produced it. Configuration and code changes can then be checked against explicit expectations rather than judged from a demonstration alone.

Supported scenarios and guarantees

Choose a supported scenario family to explore the behaviour that matters to your application. Each family defines the strategies, storage, events and faults it can exercise. Workbench checks those limits before execution.

Fleet: ordering and history

Check reports from multiple sources, select the latest value by sequence and retain bounded history. This family uses memory storage and does not include restarts.

Orders: combine independent reports

Exercise entity mapping, source priority, required contributions and progress watermarks with SQLite storage. The Order recovery family also checks retained receipt identity and progress through an explicit restart.

Sports: corrections and retirement

Check first- and latest-revision policies, counts, sums and progress, including atomic retirement within a view. This family uses SQLite storage and does not include restarts.

Freshness and recovery

Check receipt-age behaviour across controlled stops and starts. Memory restarts start empty; SQLite restores durable state. These bounded arrival-based scenarios also support explicit wall-clock adjustments.

Receipts and retries

Exercise fixed link delays, lost receipts and exact retries in the supported arrival-based memory profile. Check that a retry produces the expected receipt and view, without depending on real network timing.

Configure your own static views

Combine arrival, latest-by-sequence and history fields with aliases in bounded configurations. The static memory family supports explicit conversion of supported ordinary scenarios, without retries or restarts. The static recovery family adds memory or SQLite storage, controlled orderly or abrupt restarts between completed turns, explicit reconnects and exact retries. Memory starts empty; SQLite restores durable state. Both families use zero-latency links; the recovery family excludes transport faults and automatic retries.

What repeats, and under which conditions?

With the same scenario, configuration, seed, runtime files and recorded environment, the supported runtime results repeat. Replay executes the scenario again and checks its newly produced trace against the saved evidence. A changed runtime or environment needs a new run; replay is not a promise that different versions will produce identical results.

These are specific, tested combinations. Support in one family does not mean every feature can be combined with every other feature. Unsupported configurations are rejected before execution. Variable network delays, partitions and arbitrary crashes in the middle of a commit are outside the current timeline model.

Evidence that the controls work

Selected qualification runs deliberately pause host execution and require the recorded sequence of runtime results to remain unchanged. Deliberately incorrect strategy implementations must fail the scenario’s expected results. Selected cases also compare timeline outcomes with an ordinary ZooGlass service run. These checks test both the runtime’s behaviour and the simulator’s ability to detect a wrong result.

Retained qualification covers the current families on macOS arm64. Linux arm64 evidence covers the original document campaign, not the later families. Evidence records its exact environment; bundles do not include executable dependencies. Full profile limits and reproduction instructions are in the technical guide.
