HOW IT WORKS / A WORKED EXAMPLE

Two sources.
One explicit decision.

A primary courier reports sequence 2. A backup reports sequence 900. Which one should your order view show?

An illustrated walkthrough of source priority, not a running service.

IN THIS EXAMPLE

  1. Declare the relationship
  2. Follow the publications
  3. Keep the context

First, declare the relationship.

The couriers use different identifiers. Configure shipment-3 and tracking-8 to resolve to order-42 in this view. Each source keeps its own publication identity and ordering.

The delivery field accepts both sources, uses latestBySequence for each source’s candidate, and ranks the primary before the backup.

THE RULE

Keep each source’s latest contribution.
Show the first present source in the priority list.

These are exact, configured mappings. ZooGlass does not infer relationships, compare sequence numbers across sources or interpret business status strings.

The view includes its context.

An HTTP snapshot separates the selected data from provenance: the source ID, epoch and original source entity. An acknowledgement records each matched view’s original processing outcome.

With SQLite enabled, candidates, visible state and publication identities commit together. Hidden backup updates survive restart, and retries of retained identities return their original outcomes.

Silence doesn’t change the winner.

The current priority policy has no freshness fallback, timeout or withdrawal. A silent primary stays selected. Received history does not prove completeness, and a retry outside the identity window is rejected.

A different view can rank these same sources differently. Your application still owns domain rules, source integration and presentation.
